# Touch zoom discrepancy assessment

Status: implemented in the unpublished 1.0.7.cpp draft after the assessment. No tests or production build performed. Input cadence and live rendering have not been measured. The findings below describe the original behavior.

The draft shares fractional line pitch between text-block metrics and item layout, and no longer rounds the resulting Tiles/Content icon sizes. Drawing retains its existing pixel alignment. A zoom now carries its starting preference in presentation snapshots, allowing touch takeover to interpolate the effective preference on the existing zoom clock without inverting layout geometry. The outgoing fractional preference is sampled before a wheel/trackpad target replaces it. Direct touch samples capture the current pose instead of finishing the preceding zoom first. Trackpad and wheel retain their existing animated-target policy.

x64 and ARM64 syntax checks passed with the existing unused PageLength warning. These checks do not link the DLL or establish live smoothness. Regression work remains deferred at the user's request.

## Different input paths

- Touchscreen: two contact positions supply a span ratio through ApplyManipulationPinch with a contact anchor. ApplyRowHeight keeps a double precision preference in preciseRowHeight96, updates metrics immediately for each sample, and preserves the point under the contact. It deliberately follows the hand rather than starting a timed zoom for each sample.
- Trackpad pinch: kMsgManipulationPinch supplies a logarithmic delta without a contact anchor. ApplyRowHeight rounds to an integer preference, ignores changes within the same integer preference, clears preciseRowHeight96 and starts/retargets BeginAnimatedZoom. Fractional accumulation is retained in touchpadPinchHeight96, but rendered targets are discrete.
- Ctrl+wheel: accumulates wheel detents and changes the integer preference by two units per detent. It uses the same BeginAnimatedZoom interpolation as trackpad pinch.

Thus trackpad pinch currently behaves more like animated wheel targets than direct touchscreen manipulation. All inputs eventually share metrics/layout, but they do not reach those metrics through the same sampling policy.

## Confirmed quantization specific to text-sized icons

UpdateMetrics explicitly preserves fractional direct-input font and icon sizes. However, TileTextHeight rounds font * 1.5 before multiplying by the number of lines. ContentTextHeight does the same. Their icon sizes are defined by those blocks, so fractional input still produces discrete icon sizes:

- Ordinary Tiles: three times rounded line height, plus fixed gaps. One pixel of rounded line-height change becomes three pixels of icon-size change.
- Drive Tiles: two rounded lines plus the usage bar and gaps; two-pixel icon-size increments.
- Content: two rounded lines plus a gap; two-pixel icon-size increments.

The outer direct-input branch that avoids rounding tileText/contentText cannot recover precision already discarded inside those helpers. LayoutItem also rounds the line pitch for Tiles and Content. It must agree with the metrics helpers when changing this behavior.

Ordinary icon grids derive image size directly from the fractional preference instead of this rounded text block. Their captions and packing can still change discretely. DrawIcon also pixel-snaps the image rectangle in all modes, so eliminating text-block quantization would not make the final raster entirely continuous at subpixel scale. This shared final snapping does not explain why Content/Tiles have larger steps.

Wheel/trackpad zoom interpolates iconPx from the old size to the target size over the existing zoom clock, passing through intermediate sizes even when the targets came from rounded text blocks. That explains the perceptual contrast without assuming missing touch events.

## Additional interruption issue

When touchscreen pinch begins during zoomAnimating, ApplyManipulationPinch reconstructs a preference from iconPx in grids or rowPx in lists. The grid inverse assumes the ordinary icon-size formula. The list inverse assumes rowPx equals the base preference scaled by DPI. Neither assumption holds for Tiles or Content, whose sizes derive from font line blocks and padding. Compact rows and font minimum/cap boundaries also deserve review. The handoff can therefore change scale before the user has meaningfully continued pinching.

## Proposed fix scope

1. Keep direct touch following actual scale samples. Do not hide quantization with an extra timed animation on every sample.
2. Share the line-pitch calculation between metrics and layout. Retain fractional pitch for direct scale geometry, including the saved fractional presentation after release. Preserve deliberate settled pixel alignment where needed for text rasterization rather than quantizing the icon's whole text block.
3. Track/interpolate the effective zoom preference alongside rendered metrics so touch can take over an active wheel/trackpad zoom without guessing the preference from a mode-specific icon/row measurement. Account for direct pinch beginning during a view morph.
4. Keep trackpad's existing input policy separate from this primary fix. Making trackpad pinch directly fractional would change anchoring and responsiveness; it should be a deliberate change, rather than an incidental side effect of removing Tiles rounding.
5. Check image destination snapping and text raster reuse separately after correcting the larger quantization. Font changes currently refresh formats and invalidate width measurements per touch sample; source inspection alone does not establish that this work misses frames.

Manual comparison should include slow outward/inward touchscreen pinch in Content, ordinary/drive Tiles and ordinary icon grids; the same scale change via Ctrl+wheel and trackpad; finger release/restart; wheel-to-touch takeover; grouped anchoring, DPI, column repacking and rename/selection behavior. Numerical geometry checks and live frame/input traces answer different questions.

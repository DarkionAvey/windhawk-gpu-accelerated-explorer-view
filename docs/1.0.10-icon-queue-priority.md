# Icon queue priority

The reported `icon-queue-isolation` failure asserted that an overscan or previous
viewport icon preceded visible icons. Two paths contributed:

- `RequestVisibleIcons` intentionally yields instead of waiting for a busy queue
  lock. The regression inspected the queue before deferred demand completed.
- The demand pass sorted retained jobs before enqueueing new requests. New visible
  jobs could then be appended behind retained overscan jobs, even after a completed
  pass.

Jobs now carry the current viewport priority. Retained jobs are updated under the
existing per-tab lock, and new jobs enter ahead of lower-priority jobs in their
own provider or association lane. Equal priorities preserve insertion order.
Worker counts, cancellation, retry limits and queue bounds remain unchanged.

The regression forces lock contention, checks that a follow-up is scheduled,
waits for the demand completion flag, then checks all queued file artwork for
visible-before-overscan ordering. Existing cancellation, navigation, blocked
provider, cross-tab and retirement assertions remain in place. No sleeps,
assertion retries or timeout increases were added.

Validation: ARM64 and x64 compile/link passed; `icon-queue-isolation` passed as an
individual test. `adaptive-image-demand`, `adaptive-image-pipeline` and
`shell-overlays` also passed individually using the same compiled executable.
The full suite was not run; these checks do not measure live Explorer performance.

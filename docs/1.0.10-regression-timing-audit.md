# Regression timing audit

## Scope

Searched the 95 `tests/*smoke.h` headers for asynchronous request/delivery calls,
immediate pending/queue assertions, fixed sleeps, bounded paint loops and
wall-clock animation samples. Read the relevant fixtures, manifest callers and
production request/paint paths. This is a static audit: the findings below
identify unsafe assumptions or coverage risks, not newly reproduced failures.
No regression code or mod code was changed and no tests were run for this audit.
The earlier icon-queue fix is separate.

## Highest-priority request/delivery findings

- `tests/drag-preview-smoke.h:12-26,48-59`: calls `RequestVisibleIcons` once,
  then waits using `ReceiveIcons(state,false)`. That receiver explicitly leaves
  `viewportDemandPending` set and does not resume demand. If the original pass
  yielded its queue lock or stopped before admitting drag artwork, waiting for
  pixels cannot finish the missing request. Drive pending demand through the
  owner frame/demand phase while awaiting the actual image result.
- `tests/adaptive-image-smoke.h:112,149,175,192,196` and
  `tests/icon-sizing-smoke.h:38`: assert that one `RequestEntryIcon` call must
  succeed. `QueueImageRequest`/`QueueIcon` intentionally return false and schedule
  follow-up work when a live worker owns the queue lock. A successful previous
  delivery does not prove that worker has stopped touching the lock. Separate
  successful admission from the pixel/result assertions and await admission
  through the normal bounded continuation. A fresh, worker-free first request
  is less exposed than repeated requests on an existing tab.
- `tests/adaptive-image-smoke.h:153-159` also uses one-shot viewport demand
  followed by delivery-only waits, like the drag-preview test. Its cancellation
  assertion at line 133 is different: owner-side cancellation happens before
  the queue try-lock, so that immediate assertion is not itself the same bug.

## Animation clocks

- `tests/appearance-smoke.h:50-61`: backdates a real clock by 20 ms, draws, and
  requires an intermediate opacity before an 80 ms animation settles. A scheduler
  pause before drawing can make the intermediate sample equal the endpoint.
- `tests/grid-smoke.h:586-595`: backdates zoom by 90 ms and immediately requires
  `zoomAnimating` plus an intermediate cell position, without holding the clock
  across that sample. The later retarget block correctly uses a held clock;
  that later scope does not protect the earlier assertions.
- `tests/selection-smoke.h:170-184`: repeated clicks must preserve a fade's
  original start while the real clock continues through six input transactions.
  Freeze the intended intermediate instant when testing fade continuity.

These paths are reachable through release tests, including `graphics-isolation`;
`TestIconGrid` also runs in the focused `animation-continuity` entry.

## Compositor timing

`tests/column-fit-composition-smoke.h:89-96` and
`tests/row-composition-smoke.h:107-116` assume DWM statistics advance after a
65/80 ms sleep. A sleep does not acknowledge a compositor frame. The row test
then paints and expects the original active atlas to survive, which can also
fail if the owner resumes after the animation has finished. Wait for an actual
compositor clock/frame change for liveness; use held CPU animation samples for
intermediate-state assertions. These are separate clock domains.

Not every sleep is wrong. For example, the delayed first-paint test in
`animation-smoke.h:477` checks that an unsubmitted animation has no origin, and
its subsequent intermediate/retarget assertions already use held clocks.

## Fixed iteration counts

`tests/dense-grid-smoke.h:160,233`, `tests/cold-text-smoke.h:41`,
`tests/resize-text-smoke.h:197,255,271`, and `tests/layering-smoke.h:207` warm
text with 30/100/300 paint attempts. Text raster preparation is governed by a
real QPC budget, so each attempt can build different amounts under load. These
are additional risks to validate, rather than claimed reproduced failures.
Await the pending/completion state for warm-up; keep any intentional work-budget
assertion separate, with an independent expectation.

## Possible false pass

`tests/item-tip-smoke.h:405-408` cancels a tip, sleeps 50 ms, drains currently
posted result messages and asserts that no tip appeared. If the provider has
not completed by then (or never entered before cancellation), the assertion
can pass without exercising a stale reply. Gate the real provider/result stage
and observe its completion before checking rejection of the cancelled result.

## Recommended order

1. Fix admission and delivery-only waits in the image tests.
2. Hold animation clocks around intermediate-state assertions.
3. Use compositor completion observations instead of fixed-time assumptions.
4. Replace warm-up attempt counts with completion waits, preserving budget checks.
5. Make the tooltip cancellation test prove a late result was actually exercised.

Keep each test independent and Parallel where appropriate. Do not add retries,
widen comparisons, increase the 120-second limit, or declare Serial to hide
these timing assumptions. Validate changed tests individually, as requested.

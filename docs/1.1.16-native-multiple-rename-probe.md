# native-multiple-rename: Windows' own probe loses its editor

The first block of `TestNativeMultipleRename` (a plain ExplorerBrowser with
no GPU overlay, on the test's private desktop) fails with
`native rename control did not show its edit window`. The mod's own DefView
rename cases in the same test pass.

## What was measured (WH_CBT / WH_CALLWNDPROC traces, 1.1.16)

- `IFolderView2::DoRename` returns S_OK and creates no editor synchronously.
- In a single later dispatched message, DefView creates its `Edit`
  (under `CtrlNotifySink`), focuses it, and focus then moves straight back to
  `DirectUIHWND`. The editor is destroyed right afterwards. No message is
  dispatched between the editor gaining and losing focus, so per-message
  polling cannot catch it.
- The focus change back comes from Explorer's DirectUI items view:
  `explorerframe.dll` called through `DUI70.dll`/`DUser.dll`, from the
  probe's own `DispatchMessageW`.
- No `WM_ACTIVATE`/`WM_NCACTIVATE`/`WM_ACTIVATEAPP` reaches the frame.
  `GetForegroundWindow()` is never the frame; a private desktop that is not
  the input desktop cannot grant foreground.

## Ruled out (the failure is unchanged with each)

- An on-screen frame without `WS_EX_NOACTIVATE`, plus `SetForegroundWindow`
  (it passed once alone, then failed alone and in the suite).
- Waiting for `OnNavigationComplete` before selecting.
- Removing `IShellView::UIActivate`.
- Selecting with `SVSI_NOTAKEFOCUS | SVSI_SELECTIONMARK`, as the mod does.
- Hiding the `CtrlNotifySink` host before `DoRename`, as the mod's
  suppression does.
- Committing on `EVENT_OBJECT_FOCUS` (out of context): it is delivered after
  the editor is gone.

## Root cause (public Microsoft symbols)

The stack resolves to `CInplaceRename::_PlaceAndShowControl` ->
`CInplaceRename::_EndEdit`, reached from `UIItemsView::OnEvent` ->
`DirectUI::Element::SetKeyFocus`. `_PlaceAndShowControl` positions the edit
successfully (`SetWindowPos` returns TRUE), then calls
`CInplaceRename::_HookMouse`. That calls
`SetWindowsHookExW(WH_MOUSE, proc, explorerframe.dll, ownThread)`, which fails
with error 126 (`ERROR_MOD_NOT_FOUND`), and `_PlaceAndShowControl` ends the
edit with E_FAIL.

On this machine a thread hook backed by any DLL fails with 126 (System32 DLLs,
`windhawk.dll`, `libc++.whl`), on the default desktop as well as a private
one, in a plain standalone process. Only a hook backed by the EXE's own
module succeeds. `SetWindowsHookEx*` in user32 and `NtUserSetWindowsHookEx`
in win32u are unpatched. Windhawk injects `windhawk.dll` and the installed
mods into every process, including the test runner.

Later checks with Windhawk fully exited, in both normal and elevated
terminals, still fail with 126, and Explorer itself cannot rename. Restarting
Explorer does not clear it. It is session state, not Windhawk.
`Assert-ShellHookRegistration` (tests/parallel-runner.ps1) now checks this
registration before any build or test step and stops with PENDING.

The test is right to fail. Windows' own in-place rename cannot start in a
process where this hook fails. Still to establish: whether Windhawk
injection or the OS build (10.0.26300) causes it. Compare with Windhawk
fully exited.

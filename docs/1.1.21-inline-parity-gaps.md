# Expanded folders: parity with the open folder's own items (1.1.21)

Goal: an item inside an expanded folder (Details view, inline folder tree)
behaves exactly like the same item shown as a row of the open folder, so the
user cannot tell the difference. Where Explorer itself prevents that, the
limit is named below so it can be probed and worked around.

Working copy: `1.1.21.cpp` (not yet built or published; `latest.cpp` is
1.1.20). Do not run the full suite or `build.bat` until the user asks.

## How the parity tests work

- Live tests use a real private ExplorerBrowser over a private fixture under
  the regression temp folder: `InlineLive::Live` in
  `tests/inline-dirs-live-smoke.h`. `MakeTree` builds
  `root\alpha\{a.txt,b.txt,sub\deep.txt}`, `root\gamma\{c.txt,inner\i.txt}`,
  `root\beta\` (empty), `root\zeta.txt`.
- Comparison tests (`tests/inline-dirs-live-parity-smoke.h`) show the same
  folder twice: expanded inline in one `Live` (root with `alpha` open) and
  opened directly in another (`Live open(alpha, listed)`), then compare row
  by row. `MakeParityTree` adds files of every kind to `alpha` (sizes, Office
  lock file `~$report.docx`, hidden file, Unicode name, no extension, upper
  case, a folder, a shortcut with the link overlay). `listed` is derived from
  Explorer's hidden-files setting, never hard-coded.
- Hooks are inert in the test build (`WH_EDITING`): the selection bridge,
  `CDefView::_GetItems` and `OnBackgroundContextMenu` hooks are tested through
  the functions their bodies call (`InlineSelectionViewObject`,
  `InlineMenuOwner`). The modern menu itself is verified by the live probe
  `tests/run-menu-decision-probe.ps1` (see `docs/1.1.21-native-menu-decision.md`).
- **Waits are completion signals, never outcome polling** (tests/README.md,
  "Writing a regression"; AGENTS.md). Synchronous calls are checked right
  after they return; Shell reports are delivered with `Live::Flush`
  (`SHCNF_FLUSH`), then `Live::Settled` waits for the mod's own idle state
  and judges the outcome once. A wrong outcome fails in seconds.
- Helpers worth reusing: `Live::Open/Toggle/SelectOnly/Row/Path/
  CheckConsistent/Flush/Settled/Settle`, `Present` (Details columns captured
  with `RefreshExplorerColumns`, details and overlays resolved),
  `CompareFolder`, `FolderRows`, `MenuVerbs/HasVerb`, `DropPaths`.
- Run only the tests concerned, e.g.
  `powershell -NoProfile -ExecutionPolicy Bypass -File tests/run-regressions.ps1 -SourceFile 1.1.21.cpp -Tests inline-dirs-live-parity-presentation`.
  The run stops at the first failure; run a failing test separately from the
  others to see them all. Each test takes 1-5 s plus about 2 min of compiling.
- Pitfalls met: OLE clipboard calls need `OleInitialize` on the test thread
  (Explorer's thread has it); a slow-click rename needs the list focused
  (`FocusFixture::focus = s.hwnd`, as a real click gives); shell edits through
  the Bash tool can drop backslashes in `L"alpha\\a.txt"` strings: edit test
  sources with the Edit tool and grep for single backslashes afterwards.

## Open gaps (the mod's behaviour)

1. **Intermittent Paste failure through the mod's command (watch).**
   - What: Paste onto a folder inside an expanded folder through
     `InvokeInlineSelectionCommand(s,"paste",CMIC_MASK_FLAG_NO_UI)` returned
     false in about half the runs (with a Shell beep), while the same verb on
     a fresh menu object succeeded right after. The mod logged nothing, so the
     failure was before `InvokeCommand` or with `ERROR_CANCELLED`.
   - Since the deterministic rewrite (no polling, clipboard checked right
     after Copy/Cut) it has not recurred. If it does, the test prints the
     direct verb's HRESULT (`PARITY paste onto ...`).
   - Possible cause, not proven: the real clipboard was unavailable at that
     moment. A locked session denies it (`OpenClipboard` error 5, Copy leaves
     nothing, `OleGetClipboard` `CLIPBRD_E_CANT_OPEN`); the test now checks
     this first and names it. Windows' clipboard history (enabled on the dev
     machine) also opens the clipboard after each change and could collide
     with an immediate Paste. Not confirmed.
   - 2026-11-28, session unlocked, clipboard history on: the test passed
     alone through the runner and then 20 times in a row (40 Pastes, each
     right after its Copy/Cut), with no failure. Clipboard history did not
     collide. The remaining explanation is the locked session (earlier
     unattended runs). Not reproducible now; kept as watch until a full
     unlocked suite run passes it.
   - Differences between the mod's call and the direct one: the mod passes
     `CMIC_MASK_UNICODE` with `lpVerbW`, `hwnd = frameHwnd`, and sites the
     menu on `state.shellBrowser` (`InlineMenuInvocation`).

2. **A cross-folder set rename can lose the whole selection (under load).**
   - What: `inline-dirs-live-rename-sets`, set `alpha\set (2).txt`,
     `gamma\c.txt`, `zeta.txt` renamed to `mix`: the rows took their new
     names, but after the re-list nothing was selected (the native view held
     nothing either). Seen in 2 of 5 full parallel runs; never alone or with
     the inline-dirs tests only.
   - Suspected, not proven: the set includes an open-folder row (`zeta.txt`,
     mirrored in the native view). After the mod's `IFileOperation` (native
     selection imports are deferred during `NativeFileCommandScope`), an
     empty native selection is imported (`ApplyImportedNativeSelection`, not
     an echo since the counts differ) and replaces the GPU selection,
     including the GPU-only children. Possible origins: DefView drops the
     renamed item's selection, or the mirror of `zeta.txt` was still pending
     on the selection lane when the set was renamed.
   - Evidence still needed: the test now records the mod's `[GPU selection`
     log lines and the selection right after the commit, printed only when
     it fails. Run the full suite (unlocked) until it recurs, then fix the
     import contract from that log, without guessing.

## Fixed during this work (for reference)

- Test fixtures under load: `inline-dirs-live-parity-presentation` (folder
  times in the parent's index are written lazily by NTFS; the fixture now
  sets each folder's times on a handle so the index copy is written) and
  `inline-dirs-live-parity-item-tips` (relative "N seconds ago" text moved
  between the two tips; the fixture items now carry a fixed 2001 date). This
  covers the "Watch" item about `alpha\sub`'s raw modified time.

- A folder refresh report (`SHCNE_UPDATEDIR`: refresh, coalesced bursts of
  changes) now re-lists that expanded folder. Filesystem watches subscribe to
  it too (before, only namespace folders did); the open filesystem folder
  still uses its own directory watch, and the identity is cloned only while
  the tab has expanded folders. Test: `inline-dirs-live-folder-refresh`. The
  clipboard test also expected rows of `alpha\sub` without expanding it; it
  now expands it.
- Audit: the selection bridge took every `SVSI_EDIT` request while inline
  children were selected, including Explorer's edit of a just-created item
  (New folder, Ctrl+Shift+N), which would have renamed the old selection.
  `BridgeInlineRename` now acts only when the requested item (by leaf name, as
  a child's ID is relative to its own folder) is selected. Test:
  `inline-dirs-live-rename-bridge-target`.
- Audit: a single inline rename failure showed its own `FormatMessageW` box
  inside the rename transaction; it now uses the same posted shell32 "Cannot
  rename" notice as a failed set (`ReportMultipleRenameFailure`).
- Audit: `ReceiveInlineTreeResults` revealed the returned-from folder while
  the rebuild was still held for an open rename field; it now reveals when
  the held rebuild runs.

- An unrelated change closed an open rename field: `RegraftInlineTree` now
  holds the rebuild while a field is open (`inlineTreeRegraftDeferred`),
  `FinalizeDestroyedRenameEditor` posts `kMsgInlineTreeReady`, and
  `ReceiveInlineTreeResults` runs the held rebuild; the edited item's own
  removal still closes the field first. Same contract as the open folder
  (`TestRenameEditedItemRemoved`). Test: `inline-dirs-live-rename-edited-removed`.

## Explorer limits

- Creating a new item inside an expanded folder: Explorer's New menu and
  Ctrl+Shift+N always create in the open folder. Not probed yet; a mod
  route would be the expanded folder's own New menu (its folder background
  menu) on that folder.

## Parity tests still to write

The ten from the minimum list are written (`tests/inline-dirs-live-input-smoke.h`,
see Verified). Left out of them, on purpose or for later:

- Plain Delete through the key route: it recycles, and tests never touch the
  Recycle Bin. Shift+Delete takes the same route with the Shift flag.
- Ctrl+C/X/V through the key route: the real clipboard (Serial). The commands
  themselves are covered by `inline-dirs-live-clipboard-commands`.
- Undo after a delete or move: a delete recycles; a move needs the clipboard.
- Undo after a rename (`inline-dirs-live-parity-undo`, focused only): the
  folder menu offers "Undo Rename" and invoking it succeeds, but the file is
  not renamed back within 30 s in the test host (it did pass earlier runs).
  Cause unknown; probe Ctrl+Z on a nested rename in live Explorer. Windows
  can also stop recording renames until a restart (native Explorer too):
  `run-regressions.ps1` now checks this first (`--check-shell-undo`) and
  asks for a restart.
- Touch swipe (marquee) selection on nested rows: tap and press-and-hold are
  covered; mouse marquee is.
- Opening a nested file with several items selected (default command on the
  selection) would launch the item's application; only one file is opened
  (its launch is recorded, not run).

## Not testable in the regression process

Explorer's status bar reads the selection through the hooked
`IFolderView::ItemCount/Items`; hooks are inert in the test build, so the
status bar itself is checked live only. The count it receives is the item set
verified by `inline-dirs-live-selection-objects`.

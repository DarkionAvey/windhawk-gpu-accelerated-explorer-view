# VRAM reduction options (to benchmark)

Context: 1.1.17 removed resize flicker by never replacing a visible tab's swap
chain for a smaller viewport. Lane buffers are created and grown to the frame's
client area (`ExtendToFrameReach`), grow to the monitor work area only during
frame edge drags, and are trimmed back to the frame reach only while the
overlay is hidden (`AdvanceStandbyGraphics`). Swap chains already use the
minimum of two buffers (`kPresentationBuffers`).

Each option below must be benchmarked before adoption: GPU memory per tab
(`[GPU memory]` log, DXGI budget), number of chain rebuilds per scenario, and
whether any rebuild lands on screen. Scenarios: new tab, preview pane toggles,
splitter drag, frame edge drag, maximize/restore, tab switching with 1/5/10
tabs, monitor change.

Benchmark: `--test vram-tabs-4k` (focused, `tests/vram-bench-smoke.h`): ten
tab hosts in one 3840x2160 frame over the 512-item fixture, pane toggles,
splitter steps and an edge drag per tab, then three rounds of tab switches.
Baseline (1.1.17, three runs): 632.8 MiB of swap chains, ~1470 MiB process
local VRAM, 0 visible replacements, longest switch ~39 ms.

1. **Release background tabs' swap chains — tried in 1.1.18, rejected.**
   Implementation: release the chain in `AdvanceStandbyGraphics` when the
   overlay is hidden, rebuild it in `EnsureTarget`, keep a returning tab
   hidden until the first accepted frame, republish on `WM_SHOWWINDOW`
   (`SW_PARENTCLOSING`) because Explorer hides the tab host, not the overlay,
   and `QueuePresentationModel` skips already-inactive tabs.
   Result: 569-633 MiB of chains (at most one hidden tab without a chain),
   longest switch 47-80 ms. Standby itself paints (mode-scene retirement,
   pulses), and any paint recreates the chain off screen, so released images
   come straight back. Every return also waits one to two frames for a first
   image. Do not retry as a patch: it needs standby to never paint once the
   image is released, and it still costs switch latency.
   Original note: Largest saving (every hidden tab
   holds a full chain, roughly 26 MB at 2476x1327). Rebuild while the tab is
   shown again; the content change of a tab switch hides the rebuild. Risk: the
   switch-back path presents the retained image immediately
   (`PresentCachedTabSurface`); the first frame must arrive without a gap.
   Measure: total chain bytes vs tab count, switch-back time to first frame.

2. **Exact height, frame-reach width — adopted in 1.1.18.** Result (five runs):
   550.8 MiB of chains (-13%), ~762 MiB process local VRAM (-48%; more than
   the height alone explains, driver allocations appear to scale with it),
   0 visible replacements. Verified flicker-free live; guarded by
   `pane-resize-presentation-*`. Original note: Explorer's panes and splitters only
   change the list width; height changes come from frame sizing/maximize,
   which already use their own path. Saves ribbon/address/status rows (about
   15% per tab on a 1327 of 1565 layout). Measure: bytes per tab, rebuilds
   during pane toggles (must stay zero).

3. **Width capped at frame minus navigation pane — rejected.** About 11% per
   tab, but hiding the navigation pane rebuilds the visible chain: a flicker on
   a panel toggle. Original note: Saves the navigation pane
   width (typically 300-400 px) but hiding the navigation pane would rebuild
   once on screen. Lowest priority; only if 1 and 2 are insufficient.

4. **Trim work-area buffers after an edge drag — rejected (no measurable
   benefit).** Only the visible tab ever holds the excess (hidden tabs are
   trimmed off screen), bounded by work area minus frame. Original note:
   A visible tab keeps work-area buffers after WM_EXITSIZEMOVE until it goes
   off screen. Trim at the next navigation, view-mode switch or zoom, where the
   content change hides the rebuild (event driven, no timer). Measure: bytes
   held after a drag, rebuild visibility.

5. **Shared D2D device across tabs — deferred, needs a design.** The only
   remaining real saving: ~21 MiB per tab beyond the chains. Conflicts with
   tab-owned devices on independent lanes. Original note: Each tab device has its own internal
   cache (capped at 16 MB). Large refactor; measure first.

# Hidden native layout audit

## Release comparison

The public files in releases were inspected without modification.

- 0.9.240 already collapses native presentation children and saves their rectangles. Its item menu uses IShellFolder::GetUIObjectOf, IContextMenu::QueryContextMenu and TrackPopupMenuEx (releases/0.9.240.cpp:19505). Opening that popup does not ask CDefView to validate the mouse against its hidden list. Stale bounds could still affect native restoration; the older menu path avoided exposing this dependency.
- 1.0.4 forwards menu requests through native WM_CONTEXTMENU and temporarily expands presentation children (releases/1.0.4.cpp:25075). Its PreserveNativeContentLayout repairs empty child bounds, not stale nonempty bounds (5976). SetNativeInputLayout returns immediately if already expanded (6004), and restoration replays saved bounds (6091).
- The retained development history starts at 0.9.341, which already forwards native context menus. Input-layout expansion appears between retained 0.9.345 and 0.9.346. These files cannot establish the exact first introduction of native menu forwarding, because earlier development sources are unavailable here.

This explains why an older public release could appear unaffected by right-click failures. It does not establish that its native restoration geometry was correct in every situation.

## Evidence and mechanism

The supplied log records a GPU viewport of 2146 by 1911 and native restoration at 1503 by 1911, leaving a 643-pixel width mismatch. It establishes stale native geometry, but does not identify the first historical resize that lost it.

The code relied on native child WINDOWPOS notifications to keep saved bounds current while intentionally hiding the host and collapsing its presentation child. Hidden parent layout can be skipped. In addition, PreserveNativeContentLayout resizes the Shell parent under a thread-wide internal visibility flag; genuine synchronous child layout generated by that resize was excluded from recording by the same flag. Thus even receiving a child layout request was not sufficient to preserve it.

There were separate copies of geometry: current host client size, Shell view size, saved child rectangle, and expanded native input size. Nonempty child size and an already-enabled input flag were incorrectly used as freshness checks. Restoration also replayed the cached rectangle without reconciling its parent.

## Draft fixes

1. Record the parent client size with each native child rectangle. Reconcile direct Shell children against their current parent while retaining measured edge insets. Nested/shared controls retain their independently observed bounds; empty parent sizes do not replace usable geometry.
2. Reconcile before every menu expansion, including repeated expansions, and before native restoration. Repair an expanded stale nonempty child as well as an empty child.
3. Keep the visibility/reentrancy guard, but exclude geometry recording only for the exact viewport the overlay is writing. Native child layout triggered by a parent visibility/resize transaction remains observable. The scoped target restores the previous target through nested calls.

All changes stay on the owning UI thread. No provider work, timers, polling or assumed UI dimensions were added. Native-host suppression remains in force before layout.

## Adjacent paths reviewed

- Host WINDOWPOS changes queue existing owner-thread presentation reconciliation; overlay positioning suppresses/reconciles before reading host geometry.
- Tab activation/view handoff uses that presentation path, with lifetime/window ownership checks. Menu entry separately verifies the active native view and navigation identity.
- Minimized/empty client sizes retain the last usable layout. Resuming or opening a menu re-evaluates the live parent; restoration does likewise.
- Menu collapse messages validate lifetime and recheck active menu/popup ownership. An input action clears a pending invocation with no popup; no elapsed-time assumption was introduced.
- Native fallback/unload hide the GPU surface before restoring native children and host visibility. Reparented or foreign-root windows are not resized.
- Rectangle mapping retains MapWindowPoints handling for mirrored windows. DPI changes can trigger genuine native layout updates; the narrowed guard preserves those requests rather than assuming old insets override a new native request.

These are source-path findings, not proof of all live Explorer interleavings.

## Regression coverage and limits

The new native-viewport-resize entry uses a private real ExplorerBrowser with Details, Icons and Tiles, grow/shrink sequences, collapsed and already-expanded input layout, and native restoration. The native-suppression regression now checks a real Windows layout API request inside the internal visibility scope, retaining its independently requested rectangle/insets through a subsequent zero-size echo. No manufactured Windows messages were added.

The final draft compiled for x64 and ARM64. Native suppression and the new resize regression passed standalone. Both also passed in a Jobs 16 run. The eight related checks passed together at Jobs 16: real-native-viewport, native-menu-interaction, native-menu-archive, native-menu-delegated, native-return-routes, native-return-unload, mirrored-window-coordinates and dpi-scaled-geometry. Reports: native-layout-audit-public-09a30a835c844c03958acec193d64337 and native-layout-final-alone-80f7eb6351544c36b7b4a2547beb0922 in the Windows temporary directory.

One initial audit invocation incorrectly selected the private-desktop core return test directly; its desktop guard rejected it and cancelled pending tests. The proper public return-test wrappers created private desktops and passed. No failed product assertion was retried unchanged. Live shell:appsfolder testing remains distinct from these process-owned Shell/component regressions. No public source or archived release was changed, and no release build/publication was performed.

# Native context menu: how Explorer chooses the item or folder menu (1.1.21)

Goal: show Windows 11's modern item menu for inline children (expanded
folders) and later for non-native Miller columns, instead of the classic menu.

## Tools

- `tests/menu-decision-trace.wh.cpp`: diagnostic mod, pass-through hooks with
  stacks, active only during the probe and only in its folder.
- `tests/menu-decision-override.wh.cpp`: stage-2 diagnostic mod, the override
  below, active only in the probe's `forced-*` steps.
- `tests/menu-decision-probe.cpp` via `tests/run-menu-decision-probe.ps1`:
  opens Explorer on a private Temp folder (`top.txt`, `sub\nested.txt`) and
  requests menus (keyboard Shift+F10 and WM_CONTEXTMENU at a point), each step
  verified before the next. It prints the opened menu's entries (UIA).
  `-Symbolize <log>` resolves the trace's stacks with public symbols.

## Findings (Windows 11 26300, GPU mod disabled)

The choice is made in ExplorerFrame, before any Shell selection API is used:

- `CDefView::WndProc` (WM_CONTEXTMENU) -> `_OnContextMenu` -> `_DoContextMenu`
  -> `CItemsView::ShowContextMenu` -> `UIItemsView::ShowContextMenu`.
- `UIItemsView::ShowContextMenu` (+0x310) asks its items element a yes/no
  question (vtable slot 12) and calls, from one instruction (+0x33C), either
  `CDefView::OnSelectionContextMenu(const POINT*)` (yes) or
  `CDefView::OnBackgroundContextMenu(const POINT*)` (no). Same signature and
  `this`; only the vtable slot differs (0x20 vs 0x28).
- Item path: `OnSelectionContextMenu` -> `DoSelectionContextMenu` ->
  `CDefView::_CreateSelectionContextMenu(int, REFIID, void**)` (builds the
  IContextMenu from the view's own items via `CFSFolder::GetContextMenu`) ->
  `_DoContextMenuPopup(menu, 0x90, ...)` -> `DoCuratedContextMenu` ->
  `ContextMenuPresenter::PrepareForContextMenu` (the modern menu), which reads
  the items through `IFolderView::Items(SVGIO_SELECTION, IShellItemArray)`.
- Folder path: `OnBackgroundContextMenu` -> `DoBackgroundContextMenu` ->
  `GetItemObject(SVGIO_BACKGROUND, IContextMenu)` -> same popup/presenter.

Why the GPU mod's earlier attempts failed: answering the selection queries or
`GetUIObjectOf` cannot change the yes/no answer, which comes from the items
element; replacing the background IContextMenu kept the folder presentation.

## Stage 2: override (verified by the probe's forced steps)

While a menu is requested for items the native view does not hold:
1. `OnBackgroundContextMenu` -> call `OnSelectionContextMenu` with the same
   arguments. It opened the item presentation.
2. `CDefView::_GetItems(UINT svgio, int, REFIID, void**)` is the view's single
   source of its selected items. The menu asks it with
   `(SVGIO_SELECTION, 1, IID_IContextMenu)`: return
   `CDefView::_GetContextMenuFromObjectCollection(collection of the items,
   riid, ppv)`, so Explorer builds the menu object itself. The curated
   commands ask `(SVGIO_SELECTION, 0, IShellItemArray)`: return the items.
3. `Items/ItemCount(SVGIO_SELECTION)` -> the items (the GPU mod's selection
   bridge already does this).

Result (keyboard and mouse, nothing selected natively, `sub\nested.txt`): the
full item menu, identical to a native file's (Open, Open with, Cut, Copy,
Rename, Share, Delete, Send to, Copy as path, Compress to, Add to Favorites,
extensions, Show more options, Properties).

Failed variants, for reference: returning our own IContextMenu from
`_CreateSelectionContextMenu` gave only Open/extensions/Properties (no site,
callback or curated commands); answering `_GetItems(…, IContextMenu)` with a
non-menu object made Explorer show no menu.

Command check (probe `forced-copy-*`): with the menu object from
`_GetContextMenuFromObjectCollection`, "Copy as path" gave
`<open folder>\nested.txt` instead of `<open folder>\sub\nested.txt`. That
function builds the menu through the view's own folder with the items' last
IDs, so every command (Delete included) would name the wrong file for items of
other folders. The menu object must come from the items' own folder:
`IShellItemArray::BindToHandler(BHID_SFUIObject, IID_IContextMenu)` (the same
`CFSFolder::GetContextMenu` path, on the right folder).

Fewest hooks (probe `minimal-keyboard`): without the public
`Items/ItemCount(SVGIO_SELECTION)` answers the modern menu is not used at all
(Explorer falls back to its classic folder menu), so those stay; the GPU mod's
selection bridge already provides them.

Command results (forced menu, nothing selected natively): Copy as path gives
exactly the presented paths (one item, two items of one folder); Delete with
Shift asks Explorer's permanent-delete confirmation and removes only that file;
Rename shows no edit field (the view cannot edit an item it does not hold; in
the GPU mod the selection bridge's SVSI_EDIT/DoRename hooks start the mod's
rename instead, to be verified there).

Items of several folders (`sub\nested.txt`, `other\nested.txt`,
`other\third.txt`): the items' own folder cannot build one menu
(`BindToHandler` E_FAIL). Explorer's search view builds it through its folder
(`CDBFolder::GetContextMenu`, interface `{47D9E2B2-CBB3-4FE3-A925-F49978685982}`
method 3), but that builder and the library's (`CLibraryFolder`) accept only
their own children (E_INVALIDARG for plain items, also with the view window),
and a search folder cannot wrap arbitrary paths (`ParseDisplayName` E_FAIL).
What works: the desktop's default menu over the full IDs with the first
item's associations (`SHCreateDefaultContextMenu`, as for search results):
full modern menu (16 entries), Copy as path gives exactly the three paths. A
logging wrapper showed the modern menu treats it exactly like a one-folder
menu (same interface requests and QueryContextMenu flags 0x28594).

Intermittent: with earlier override builds a menu requested right after a
multi-item "Copy as path" twice showed no window although it was prepared.
Not reproduced in 8 alternating multi/single rounds with the final design;
watch for it in the GPU mod.

## Fewest hooks for the GPU mod

The Shell's own functions already do the work once they see the items:
- `CDefView::_GetItems` is the single internal source of the view's selected
  items: the menu object (`_GetItems(sel, 1, IContextMenu)`) and the curated
  commands (`_GetItems(sel, 0, IShellItemArray)`) both read it. One hook covers
  both. The menu object is the items' own folder's menu
  (`IShellItemArray::BindToHandler(BHID_SFUIObject)`), or for several folders
  the desktop's default menu as above; never
  `_GetContextMenuFromObjectCollection` (it uses the view's folder: wrong
  files). The GPU mod already builds both menus (`InlineSelectionMenu`).
- `CDefView::OnBackgroundContextMenu`: redirected to
  `CDefView::OnSelectionContextMenu` (called by address, not hooked) only
  while the mod itself requests the menu for inline items. Calling the item
  path directly instead would need the internal interface pointer
  (`CDefView` + 0x158 here), a layout detail more fragile than one hook.
- `IFolderView::Items/ItemCount(SVGIO_SELECTION)`: required (without them the
  presenter falls back to the classic folder menu); the selection bridge
  already hooks them.
Not needed: `_CreateSelectionContextMenu`, `OnSelectionContextMenu` hooks,
`_GetContextMenuFromObjectCollection`, any Windows.UI.FileExplorer hook.

Symbol hooks change between Windows builds; when a symbol is missing the mod
keeps the classic menu.

# Inline folder trees: Miller columns and expandable folders (drafted at 1.1.3)

Status: planning only. No code has been written.

## Goal

One per-tab folder-tree layer with two presentations:
- **Miller columns** (List view): one column per folder along a path.
- **Expandable folders** (Details view, like KDE Dolphin): a folder row's arrow
  expands its contents indented beneath it, with no navigation.

Both use the same models, enumeration, selection and actions, described in
"Shared folder-tree layer" below. The Miller section follows first.

When Explorer is in **List** view and the user turns on a new option, the
overlay shows Finder-style columns: one column per folder along the path. No
new view mode goes into Explorer's menus. With the option off, List view stays
exactly as it is today.

## Reference behaviour: macOS Finder column view

These are the conventions users will expect. Items marked *(verify)* should be
checked on a real Mac before they are implemented.

**Layout**
- Columns run left to right. Each column lists one folder; the column to its
  right shows the contents of the folder selected in it.
- The first column is the folder the window was opened at (for example,
  Documents chosen from the sidebar), not the disk root. Going to the enclosing
  folder (Cmd+Up) adds parent columns on the left and starts the path there.
- Folder rows end with a ">" chevron. File rows have none.
- The selected row in the focused column uses the accent colour. Selected rows
  in other columns (the path) use a muted grey.
- Selecting a file adds a **preview column** at the end: a large thumbnail or
  icon, the name, and metadata (kind, size, created, modified, last opened).
  View Options can turn it off.
- When the columns are wider than the window, the view scrolls sideways and
  keeps the newest or focused column in view.
- Long names are cut short with "…", in the middle of the name *(verify)*.

**Column widths**
- Each divider has a grip at the bottom. Dragging it resizes that column;
  Option+drag resizes all columns.
- Double-clicking the grip sizes the column to its longest name; Option+double-
  click does that for every column.
- Widths persist per window *(verify scope)*.

**Selection and keyboard**
- Up and Down move within a column. Typing a name selects within the focused
  column.
- Right moves into the selected folder and selects its first item. Left goes
  back to the parent column, keeps the folder there selected, and closes the
  columns to its right.
- Cmd+Down (or double-click) opens the item; Cmd+Up goes to the enclosing
  folder; Space opens Quick Look.
- Multiple selection (Shift, Cmd) is limited to one column. With more than one
  item selected there is no child column; the preview shows a count
  *(verify)*.
- Clicking any row in an earlier column makes that column the focused one and
  closes the columns after it.

**Other**
- One sort order applies to every column *(verify how groups appear in
  column view)*.
- Drag and drop works onto folder rows in any column, and spring-loaded
  folders open as columns while dragging.
- Back and Forward step through folders visited *(verify whether every column
  change counts as a history step)*.

## Chain root: external launches and going up from the first column

Applies to Miller columns only. Expandable folders keep the native folder as
the root and are unaffected.

**What other file managers do**
- **Finder:** the first column is the folder the window was opened at, not the
  disk root. Cmd+Up adds the parent column on the left. A reveal
  (`open -R`, "Show in Finder") selects the item in the window *(verify on a
  Mac: does the first column become the enclosing folder, or does the path
  start at the volume or home folder?)*.
- **KDE Dolphin** (new Columns view, 2026): the folder you open is the first
  column. Up, Back and the breadcrumb add its parent in front. The post does
  not say what Left does in the first column.
- **win-finder** (Windows Finder clone, PR #6): a location with no recorded
  root starts at the home folder, or at the drive or UNC share for folders
  outside home, instead of at the folder itself. The recorded root survives
  leaving and re-entering column view.
- **Nautilus:** no native column view (a third-party add-on exists).

**Plan**
1. **Root = the folder Explorer opened at, plus its ancestors on demand.**
   An external launch (Firefox "Show in folder", `explorer /select,`,
   `SHOpenFolderAndSelectItems`, a shortcut) starts the chain at the native
   folder, with the selected item focused in it, as Dolphin and Finder do.
   No prefetching of ancestors (decision 5). Anchoring at home or the drive
   as win-finder does would fill a deep path with columns the user didn't
   ask for and push the focused column off screen.
2. **Selected item from a reveal:** if the reveal selects a folder, don't open
   its child column automatically; it opens when the user moves into it,
   so a reveal looks the same as clicking the item.
3. **Going up from the first column** (Alt+Up, Explorer's Up button, Left
   in the first column): get the parent with `ILRemoveLastID` on a clone of
   the folder's PIDL (or `IShellItem::GetParent`, which follows the Shell's
   own parent for libraries, This PC and shell folders), prepend it as a
   column with the old folder selected, and make it the native view. The
   existing columns stay. Backspace keeps Explorer's meaning (Back).
4. **Left in the first column with no parent** (Desktop root, search
   results): nothing happens, as in a list. Don't wrap or beep.
5. **Visible width:** prepending keeps the focused column in view through
   the existing horizontal scroll path; columns that scroll off the left are
   kept while they are still on the path.
6. **Root is per tab and not saved.** A new window, tab or external launch
   starts at its own folder. Address bar, sidebar and Back/Forward outside
   the chain end it (decision 1) and the destination becomes the new root.
   Back/Forward inside the chain move the focus without rebuilding the
   root.
7. **Duplicate external launches into an open tab** (Explorer reusing a window
   for the same folder): treat it as a new selection in that folder's
   column; keep the chain if the folder is already in it.

**Tests to add:** `SHOpenFolderAndSelectItems` on a private fixture folder
(root = that folder, item focused); Up from the first column prepends exactly
one column and keeps selection; Left at the namespace root is a no-op;
library and zip parents come from `IShellItem::GetParent`.

## Windows mapping

| Finder | Explorer equivalent in column mode |
|---|---|
| Right / Left | Same; List view's own wrapped-column arrows aren't needed, because each column scrolls vertically |
| Cmd+Down / double-click | Enter / double-click, through the native view (opens files, enters folders) |
| Cmd+Up | Alt+Up; Backspace keeps Explorer's meaning |
| Back / Forward | Alt+Left / Alt+Right, Explorer's history |
| Space (Quick Look) | No equivalent; Explorer's preview pane stays independent |
| Column order | Mirrored in RTL layouts: the path grows from right to left |

## Reconciliation model (the main question)

**Rule: the focused column is the native view.** Every other column is a
GPU-drawn, read-only view of an ancestor folder (or of the selected child)
and is never shown to Explorer as a view.

- **Native tab's folder** = the folder of the focused column. Selection, focus,
  rename, delete, clipboard, context menus, Enter, sort changes, status bar,
  accessibility and the address bar all keep going through the existing native
  integration, unchanged.
- **Moving focus to another column** (Right, Left, or a click) calls
  `IShellBrowser::BrowseObject` on that column's folder with
  `SBSP_WRITENOHISTORY`, so arrowing doesn't fill the Back stack (to be
  confirmed in the spike), then selects the path item through the existing
  native selection code. The mod's navigation-transition path already keeps
  the old frame on screen until the new view is ready, so columns don't blink.
- **Ancestor and child columns** are enumerated on the tab's own background
  lane with `IShellFolder::EnumObjects`, keyed by PIDL. They use the existing
  icon and thumbnail pipeline and caches, and each column has its own
  `SHChangeNotifyRegister` subscription, so renames and deletes in an ancestor
  update its column. Each column belongs to its tab; nothing is shared across
  tabs.
- **Sort**: read the native `IFolderView2::GetSortColumns` and apply the same
  property and direction to the other columns with the mod's existing
  shell-property comparator. Changing the sort in the focused column
  re-sorts all of them. Groups: show none in the non-native columns, and never
  change the native grouping, which Explorer saves per folder.
- **Acting on a row in a non-native column** (right-click, drag onto a
  folder): make that column native first, as Finder does. To avoid waiting for
  navigation before a context menu or drop target can appear, the first step
  can use the folder's own `IShellFolder::GetUIObjectOf` (`IContextMenu`,
  `IDropTarget`). These are the same Shell objects the native view would use.

**Rejected:** keeping the native view at the root and drawing every column
ourselves. It would cut selection, rename, the status bar, accessibility and
the address bar off from the real view, which goes against how the overlay
reconciles with Explorer.

## Decisions (owner review)

1. **Saved view modes: the chain overrides the presentation, never the
   setting.** A chain starts at a folder whose native mode is List with the
   option on. Every folder reached through the chain is drawn as a column,
   whatever its saved mode; the mod never writes a mode or icon size to
   Explorer. The native view underneath shows that folder's own saved mode,
   hidden as usual. If the user picks a view mode while a column is focused,
   the chain ends and they see that folder's native look. Navigating from
   outside the chain (address bar, sidebar, Back/Forward to a folder that
   isn't in the chain) ends it; the destination starts a new chain only if it
   is itself in List mode.
2. **The overlay leads, the native view catches up.** The focused column is
   the folder Explorer is navigating to. The overlay shows the column's own
   enumeration immediately; the native view is asked to navigate and is
   reconciled once it's ready (order, selection, identity). Actions that need
   the native view before it's ready (rename, Enter, delete, clipboard) wait
   for it, or use the folder's own `GetUIObjectOf` objects where Explorer
   would.
3. **Latency** is covered by benchmarks (column move to first frame, and
   native catch-up), reported as CPU and offscreen measurements, not as
   displayed frame rates.
4. **Special namespaces play along.** If a child reached through the chain
   is a zip, library, cloud folder, This PC or a network location, it becomes
   a column like any other, using its Shell enumeration. The chain never
   breaks partway. Only entry points without a parent path (search results)
   don't start a chain.
5. **Memory and enumeration: only on demand.** A column is enumerated only
   when it's shown. No prefetching of sibling or child folders. Typical
   folders (a few hundred items) fit the existing per-tab pipeline. A closed
   column releases its data; icons stay in the tab's shared, budgeted cache.

**Remaining risk:** Narrator sees only the native (focused) column until the
other columns get UIA providers.

## Architecture: fragments or a new format?

Measured in 1.1.3: `ViewState` is about 1,200 lines of fields, and 789
functions take `ViewState&`. It mixes three things in one struct:
- **window and presentation**: the overlay HWND, D2D target, swap chain,
  native-host suppression, input, animation clock;
- **native binding**: `nativeHwnd`, `folderView`, Shell events, rename,
  selection sync, column-header drag;
- **folder model**: entries, sort, groups, selection mirror, enumeration
  generation, change notifications.

**Separate overlays per column (true fragments): not recommended.** Each would
need its own HWND, swap chain and native-host suppression. Only one can be
bound to the tab's single native view. Horizontal scrolling would mean moving
windows, cross-column animations and drag selection would cross window
boundaries, and focus would move between HWNDs. That multiplies the hardest
parts of the mod (lifetime, z-order, input continuity) per column.

**Copying `ViewState` per column: not recommended.** Most of its fields would
be meaningless for a column. It would also become possible for a column to
call native APIs on a view it doesn't own.

**Recommended: one host, many folder models.**
1. **Refactor first, with no change in behaviour:** extract a `FolderModel`
   (entries, sort, groups, selection mirror, enumeration and change-notify
   generations) out of `ViewState`. `ViewState` keeps one bound model, and
   the existing suite proves nothing changed. This is the "fragment", at the
   data level rather than the window level.
2. **Columns:** the tab's single overlay hosts an ordered list of column
   models. Exactly one is **bound** (the focused column, reconciled with the
   native view). The others are **detached** (own enumeration, read-only to
   Explorer). Moving focus swaps the bound role: the target model's rows are
   handed to the existing optimistic-navigation path while the native view
   catches up.
3. **Rendering:** reuse the existing List row painter, icons, text layout and
   selection visuals, drawn per column with a horizontal offset and clip.
   Horizontal scrolling reuses the existing horizontal scroll and animation
   state. There's one target and one input pipeline per tab, as now.
4. **Lanes:** columns use the tab's existing background lanes, each with its
   own cancellation generation, so closing a column cancels only its work.
   Tabs stay independent of each other.

So Miller columns are a **presentation of List mode**, not a new view format,
built on an extracted per-folder model.

## Expandable folders (Details view)

### Reference behaviour: KDE Dolphin "Expandable folders"

*(verify against a current Dolphin build)*
- An arrow sits before each folder's icon in the Name column. Clicking it
  expands the folder's contents directly below it, indented one level; clicking
  again collapses it. Double-clicking the folder still navigates into it.
- Any number of folders can be expanded at once, at any depth.
- Right expands a collapsed folder, or moves to its first child if it is
  already expanded. Left collapses an expanded folder, or moves to the parent
  row. This is also the Windows tree-view convention, so the mapping is
  direct.
- Children are sorted within their parent using the view's sort; the other
  columns (size, date, and so on) show each child's own values.
- Selection can include items from different expanded folders, and actions
  apply to all of them.
- Expansion is per view and is lost on navigation *(verify whether Back
  restores it)*.

### Behaviour in the mod

- Option: `Expandable folders in Details` (off by default). The arrow and its
  indentation scale with DPI and icon size and mirror in RTL layouts.
- The native view stays bound to the **root folder**. Expanded children are
  detached models.
- **Grouping:** while the native view is grouped, hide the arrows (and
  collapse). Expanding inside groups gives ambiguous trees.
- **Persistence:** expansion belongs to the tab and its history entry. Back
  to the folder restores it; it is never written to Explorer's saved view
  settings.
- **Fits with existing features:** row insert and remove motion when
  expanding and collapsing; zebra striping over the flattened rows; type to
  select searches the visible rows; marquee selection crosses depths;
  Ctrl+wheel zoom rescales the indentation; column auto-fit includes the
  indentation in the Name width; cut/copy visuals and rename work on child
  rows (see Actions).

## Shared folder-tree layer

Both features are presentations of one per-tab **folder tree**:

| Part | Miller columns | Expandable folders |
|---|---|---|
| Nodes (`FolderModel`) | One per column | One per expanded folder |
| Expanded set | A single path (one child per level) | Any set of nodes |
| Bound node (native view) | The focused column; moves with focus | Always the root |
| Projection | Path laid out horizontally | Flattened rows with depth |

**Shared pieces**
- **`FolderModel` node:** identity (PIDL), entries, sort, enumeration and
  change-notify generations, and its own cancellation on the tab's lanes. A
  node is enumerated only when it becomes visible (expanded or shown as a
  column). Collapsing or closing a node cancels its work and frees its data;
  icons stay in the tab's shared, budgeted cache.
- **Sort propagation:** the native sort applies to every node.
- **Property and icon pipeline:** child rows request the same per-item
  properties and icons as root rows, on the same lanes and priorities.
- **Tree selection model:** a selection is a set of (node, item) pairs. Items
  in the bound node are mirrored to the native view through the existing
  selection code. Items in detached nodes are owned by the mod.
- **Actions layer:** builds Shell objects for the selection.
  - All items in the bound node: the native view, as today.
  - All items in one detached node: that folder's `GetUIObjectOf`
    (`IContextMenu`, `IDataObject`, `IDropTarget`).
  - Items from several folders: the desktop folder's `GetUIObjectOf` with
    absolute PIDLs gives the real Shell context menu, and
    `SHCreateShellItemArrayFromIDLists` gives the data object and
    `IFileOperation` input (see the probe results below).
  - Rename of a detached item: `IFileOperation::RenameItem` with the mod's
    existing inline editor.
- **Status bar:** it stays Explorer's own (shell32's status bar module); the
  mod only adds its view buttons to it. Explorer fills it from the native
  view's selection.
  - **Miller columns:** no change needed. Multiple selection is limited to
    one column, the focused column is the native view, so the native count
    and size are already right.
  - **Expandable folders:** a selection that includes child items is invisible
    to the native view, so Explorer would report only the root items (for
    example "1 item selected" while 3 are). Keep the item total as the
    folder's own count, but feed the selection summary for the whole tree into
    the same status bar, using Explorer's own shell32 strings for "N items
    selected" and `StrFormatByteSizeEx` for the size. No second status
    surface, and no invented text.
  - **To find out in the spike** (needs a real, private Explorer window,
    because `ExplorerBrowser` has no status bar): how this build delivers the
    text (`IShellBrowser::SetStatusTextSB` or the status module's own read of
    the view), whether the native view overwrites the mod's text on its next
    update, and the shell32 string IDs Explorer uses. If the text can't be
    owned reliably, the fallback is to leave the native text and log the
    condition, never to draw a lookalike.

### Probe: selections spanning folders (1.1.3, Windows 11 26300)

A throwaway probe (not a regression test) used a private temp fixture
(`r1.txt`, `A\a1.txt`, `B\b1.txt`) and a hidden private `ExplorerBrowser`
in Details view at the fixture root.

**The native view cannot hold items from other folders, and it doesn't
always say so.**

| Call | Result | Selection afterwards |
|---|---|---|
| `IShellView::SelectItem(r1.txt)` (own child) | `S_OK` | `r1.txt` |
| `SelectItem` with the relative PIDL `A\a1.txt` | `E_INVALIDARG` | none |
| `SelectItem` with an absolute PIDL | `E_INVALIDARG` | none |
| `SelectItem` with the foreign one-level ID `a1.txt` | **`S_OK`** | **none** |
| `SelectAndPositionItems(r1, A\a1)` | **`S_OK`** | **`r1.txt` only** |
| `SelectAndPositionItems(r1, foreign a1)` | **`S_OK`** | **`r1.txt` only** |

So the mod must only ever pass the bound node's own child IDs to the native
view, and must confirm the result by reading `GetSelection` back (the mod
already does this for other reasons), never by trusting `S_OK`. Detached
items stay in the mod's tree selection model.

**Shell objects across folders work.**

| Call | Result |
|---|---|
| `SHCreateShellItemArrayFromIDLists(r1, A\a1, B\b1)` | `S_OK`, 3 items |
| array `BindToHandler(BHID_DataObject)`, then `CF_HDROP` | `S_OK`, all 3 paths |
| array `BindToHandler(BHID_SFUIObject, IContextMenu)` | **`E_FAIL`** |
| desktop `GetUIObjectOf(absolute PIDLs, IContextMenu)` | `S_OK`; Open, Cut, Copy, Create shortcut, Delete, Properties, and third-party handlers (7-Zip) |
| `CDefFolderMenu_Create2(desktop, absolute PIDLs)` | `S_OK`, 9 items |
| `IFileOperation::CopyItems(mixed array)` without UI | `S_OK`, 3 files copied |

The mixed menu has no Rename, as expected for a multi-item selection; Explorer
search results behave the same way. The menu commands were only listed, never
invoked. To repeat this on another Windows build, copy the probe's approach
into a read-only Shell-integration regression rather than relying on these
numbers.

**Why this justifies the refactor:** the `FolderModel` extraction is needed
by both features, so it's one structural change behind one user-facing story:
"the mod can present folder trees inline". The two options can ship
separately on the same layer; expandable folders is the smaller first step,
because its bound node never moves.

## User options

- `Column view in List mode` (boolean, off by default).
- `Expandable folders in Details` (boolean, off by default).
- `Show preview column` (boolean). Its labels come from property-system
  display names, so no hardcoded text is needed.
- Column width: Finder-like per-column dragging, with a mod-wide default width
  derived from the DPI-scaled List column width Explorer already uses.

Each option needs an `OptionCatalog` entry, an effect assertion and a
`kCoverage` entry.

## Phases

0. **Refactor**: extract `FolderModel` from `ViewState` with no behaviour change; the full suite must pass unchanged. Spike: `BrowseObject` with `SBSP_WRITENOHISTORY` (history, address bar), multi-parent context menus and data objects, and latency benchmarks.
1. **Expandable folders** in Details (root stays bound): tree projection, selection model and actions layer.
2. **Miller columns**: ancestor columns read-only, with the native view as the focused column;
   mouse navigation; RTL; DPI.
3. Columns: keyboard model, horizontal scrolling, column resizing, typing to select.
4. Preview column.
5. Context menus and drag and drop on non-native columns; spring-loaded
   folders.
6. Optional UIA providers for detached nodes (columns and expanded rows).

## Tests to plan

Use a real private `ExplorerBrowser` like the existing `view-events-*` tests,
with private fixture folders:
- Navigate down three levels and back up; check history (no extra Back
  entries), selection of the path items, and that the native and GPU lists are
  never shown at the same time.
- Rename, delete and add files in an ancestor folder; check that its column
  updates through change notifications, not through a test-made message.
- Sort-change propagation; RTL mirroring; 96, 144 and 192 DPI as separate
  manifest entries.
- Expandable folders: expand two siblings and a grandchild; check row order
  and depth, sort within each parent, that the native selection holds only
  root items, and that collapsing cancels that node's pending work.
- Actions on a mixed selection (root and child items): copy, cut, drag and
  delete through the real Shell objects, on private fixtures only.
- Changes inside an expanded child folder update its rows through change
  notifications.
- With each option off: List and Details output match today's pixels.

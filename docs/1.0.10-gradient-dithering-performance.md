# Gradient dithering cost

Measured on November 13, 2026. A cached dithered texture had almost the same steady draw cost as a native gradient in this probe. Adding a noise draw over every highlight was substantially more expensive, especially on the integrated GPU. These measurements preceded integration into the mod.

The integrated GPU is **AMD Radeon(TM) Graphics**, PCI vendor/device `1002:13c0`. The benchmark explicitly selected it through DXGI and confirmed `UnifiedMemoryArchitecture=TRUE` through D3D11. There was no fallback to the RTX 4090 or software rendering. The machine has a Ryzen 9 9950X3D and Windows build 26100. A separate RTX 4090 run is retained for comparison; the recommendation below uses the integrated results.

## Workload

The standalone probe uses hardware Direct2D/D3D11 with a 2160 × 4000, 8-bit BGRA target at 96 DPI. It draws 200 compact rows, 20 physical pixels tall, with 2144 × 18 rounded highlights. Each highlight spans nearly the entire screen width. The blue gradient fades from full alpha on the left to approximately 10% on the right. Mod opacity is tested at both 100% and 40%.

The 1,000, 5,000 and 20,000 cases repeatedly draw over the same 200 row positions. This deliberately creates 5×, 25× and 100× overdraw; those cases do not represent additional visible rows on the same screen. They stress draw submission, blending and memory bandwidth. Selecting many offscreen items should not require painting every selected item; this probe does not exercise the mod's selection bookkeeping or viewport culling.

Three paths are compared:

- **Native:** cached Direct2D linear gradient brush, with the same gamma, endpoint updates and rounded fill used by the theme drawing path.
- **Noise overlay:** native gradient followed by a second rounded fill using a cached 64 × 64 black/white noise brush. Noise alpha is 2/255, further multiplied by mod opacity. The extra fill requires no per-frame bitmap allocation.
- **Cached ramp:** one rounded fill with an exact-width, precomputed ordered-dither bitmap brush. Color and opacity are baked into an 8-pixel-tall repeating ramp. It uses 68,608 bytes of pixel data per cached ramp, excluding driver/resource overhead. On the integrated GPU, setup took 0.32–0.37 ms of CPU time per ramp, including bitmap/brush creation calls; deferred GPU upload is not separately timed. Warmup excludes setup from the frame timings.

Each workload has three warmup frames and 21 measured frames per path. The ordering rotates through all six permutations. Every frame waits for its GPU timestamp query to complete before the next frame starts. No failed samples are retried.

## Integrated results

Median milliseconds, with **40% mod opacity**:

| Highlight draws | Native completed | Noise overlay completed | Cached ramp completed |
| ---: | ---: | ---: | ---: |
| 200 | 1.980 | 3.460 | 1.993 |
| 1,000 | 7.646 | 15.251 | 7.785 |
| 5,000 | 36.173 | 75.011 | 36.957 |
| 20,000 | 141.848 | 298.873 | 143.851 |

At 200 rows, the noise overlay added about **1.48 ms**, or **75%** to completed offscreen draw time. The cached ramp added **0.013 ms**, a difference too small to establish a meaningful penalty from this run. At 20,000 draws, the cached ramp was approximately 1.4% slower while the overlay cost more than doubled.

At 200 rows, CPU submission medians were 0.350 ms native, 0.637 ms overlay and 0.346 ms cached. GPU timestamp intervals were 1.797 ms, 3.264 ms and 1.804 ms respectively. At 100% opacity, completed medians were 2.005 ms, 3.528 ms and 2.025 ms. The full results include p95 CPU/GPU intervals and both opacity settings.

For comparison, the RTX 4090 completed the 200-row, 40%-opacity workload in 0.351 ms native, 0.680 ms overlay and 0.327 ms cached. These small timings should not be used to claim that cached textures outperform native gradients.

## What the measurement establishes

The simplest extra-pass noise approach has a measurable cost on a modest integrated GPU even with cached resources. A precomputed, single-pass texture is a promising way to avoid that overhead for stable geometry. It would be preferable to investigate that route before adding a second fill to every themed highlight.

The two candidates are **not visually equivalent dithering implementations**. The noise overlay can shift tones and affects areas independently of the gradient's local alpha. It is a cost probe, not a finished color-correct treatment. The cached ramp quantizes premultiplied color and alpha with ordered dithering, but its synthetic interpolation has not been pixel-matched to Direct2D. Neither candidate dithers the final Windows compositor output, and no visual quality claim is made by this timing experiment.

A production cache must account for theme, colors/stops, direction, physical width, DPI and configured opacity, and must be bounded and owned by the tab/device. Resizing, different item widths, arbitrary gradient directions and state transitions need validation. Applying animated opacity after a cached ramp can introduce quantization again; rebuilding ramps for every animation frame was not measured and should not follow from these results. A single-pass custom shader is another possibility, but was not measured here.

The subsequent `1.0.10.cpp` implementation uses eight-row ramps at power-of-two resolutions from 64 to 16,384 texels, shared across item widths. A brush transform rotates and scales the ramp to the physical gradient span; noise repeats perpendicular to the gradient. All cached resolutions together use under 3 MiB of pixel data across the three states, excluding driver/resource overhead. Each resolution is built once per tab/device, theme, appearance, accent and configured-opacity combination. Device teardown releases the brushes. Resolution changes reuse existing slots, and bitmap allocation failures retain the native gradient fallback without repeated allocation attempts for that slot.

Configured opacity is baked into each state ramp. Transitions attenuate the brush opacity without rebaking pixels, preserving the existing animation and opacity calculations. Solid fills and high-contrast behavior retain their existing paths. This generalized cache differs from the exact-width timing prototype, so the measurements above must not be described as timings of the integrated implementation. Live appearance and animation remain for user assessment.

These are isolated offscreen drawing measurements, not Explorer frame times or displayed frame rates. There is no text, icon, input, selection-model update, swap-chain presentation or Windows composition in the workload. CPU submission includes Direct2D `EndDraw` and can stall on GPU backpressure. GPU timestamp intervals can include scheduling and submission gaps; they are elapsed GPU intervals, not pure shader busy time. Completed time includes CPU work and waiting for GPU completion. Other integrated GPUs and shared-memory conditions may differ.

## Reproduce

### Visual comparison

Lossless PNG captures from the explicitly selected AMD integrated GPU:

- [Dark background, 40% mod opacity](1.0.10-gradient-dithering-dark-40.png)
- [Dark background, 100% mod opacity](1.0.10-gradient-dithering-dark-100.png)
- [Light background, 40% mod opacity](1.0.10-gradient-dithering-light-40.png)

Each sheet shows native gradient, noise overlay and cached texture in that order. It uses the exact brushes from the timing probe, with taller sample rectangles for inspection. The lower part magnifies the final 256 pixels of each rendered gradient by 6× with nearest-neighbour sampling. There is no contrast enhancement. Open the PNG at 100% when comparing full-width bands; scaling a preview can hide dithering or introduce patterns.

In these blue-gradient samples, the cached texture visibly breaks up the native gradient's broad steps on both backgrounds. The magnified crops reveal the fine ordered pixel pattern that replaces them. This supports continuing with the cached approach, but does not establish visual equivalence for other color stops, directions, widths or animated opacity.

To generate the sheets without rerunning the timing workloads:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tests/benchmark-gradient-dither.ps1 -Integrated -Visuals
```

### Timing probe

Run the opt-in probe without publishing the mod or running regressions:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tests/benchmark-gradient-dither.ps1 -Integrated
```

Without `-Integrated`, it uses D3D11's default hardware adapter. The integrated option selects a low-power hardware adapter that explicitly reports unified memory and fails if none is available. The output prints the actual adapter. Generated binaries, raw output and source/toolchain metadata are kept under `tests/.build/gradient-dither-<id>/`.

The source is [gradient-dither-benchmark.cpp](../tests/gradient-dither-benchmark.cpp). Retained measurements: [integrated GPU CSV](1.0.10-gradient-dithering-integrated.csv) and [RTX 4090 CSV](1.0.10-gradient-dithering-rtx4090.csv). CSV modes are 0 = native, 1 = noise overlay, 2 = cached ramp. CPU/GPU columns are milliseconds; `completed_median_ms` includes completion waiting.
